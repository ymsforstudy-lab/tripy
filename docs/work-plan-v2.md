# Tripy 2.0 작업 분담·순서

작성일: 2026-10-29
기준 문서: `docs/flow-v2.md` (화면·전환·결정 사항). 이 문서는 3명의 작업 분담과 순서만 다룬다.

## 분담 원칙

- **소유 파일을 나눠 같은 파일을 두 사람이 고치지 않는다.**
- 데이터 계층이 먼저 있어야 나머지가 움직이므로 A가 인터페이스를 가장 먼저 올린다. B·C는 그동안 목업 데이터로 UI를 만든다.
- `src/components/ui/`는 정리 중이다. 바텀시트(B)·BottomNav(C) 수정 전에 정리 담당자와 먼저 맞춘다.

| 작업자 | 범위 | 브랜치 | 소유 파일 |
|---|---|---|---|
| A | 데이터·인증 기반 | `feature/data-layer` | `src/contexts/*`, `src/lib/*`, `supabase/migrations/*`, `src/app/page.tsx`, `src/app/auth/*` |
| B | 여행 생성 | `feature/setup` | `src/app/setup/**`, `src/app/budget`, `src/app/nickname` |
| C | 홈 이후 화면 | `feature/travels` | `src/app/{home,expense,travels,mypage}/**`, BottomNav |

## 작업자 A — 데이터·인증 기반

1. **인터페이스 정의 → PR #1 (1~2일차, 최우선)**
   - 여행·지출 타입과 훅 시그니처를 정의한다. 예: `createTrip`, `updateTrip`, `listTrips`, `createExpense`, `updateExpense`, `deleteExpense`
   - 구현은 우선 현재 Supabase 호출을 감싸는 정도로 충분하다.
2. ~~예산 nullable 마이그레이션~~ — 예산 필수로 결정되어 하지 않는다 (2026-10-29)
3. **게스트 저장소 (localStorage)**
   - 같은 인터페이스로 localStorage 구현을 만들고, 로그인 상태에 따라 Supabase 구현과 바꿔 쓴다.
   - 익명 로그인 코드를 제거한다.
   - 2.0 첫 실행 때 기존 익명 세션이면 Supabase 데이터를 localStorage로 내려받고 로그아웃한다. 실패하면 세션을 유지하고 다음 실행 때 다시 시도한다(`docs/flow-v2.md` §5).
   - 1.x 데모 지출(`LOCAL_EXPENSES_KEY`)을 삭제한다.
4. **TripContext 홈 여행 선택 → PR #2**
   - 진행 중 > 가장 가까운 예정 순으로 고른다.
   - 지난 여행은 날짜 비교로만 판단하고 DB에 쓰지 않는다.
   - `loading`을 확실하게 노출한다.
5. **진입 분기 (01 → 03 → 07/04)**
   - Auth·Trip `loading`이 모두 끝난 뒤에만 리다이렉트한다.
   - `/`는 분기만 하고, 온보딩은 `/onboarding`으로 분리한다.
6. **닉네임 자동 생성**
   - 구글 이름을 쓰고, 없으면 랜덤으로 만든다.
   - 가입 직후 `/nickname`으로 보내는 분기를 제거한다.
7. **게스트 → 계정 이전 → PR #3**
   - 로그인하면 localStorage 데이터를 Supabase로 옮기고 기기 사본을 지운다.
   - 이전에 실패하면 기기 사본을 유지한다.
8. **확인**
   - 게스트·로그인 각각 재진입 시나리오를 확인한다.
   - 로딩 중에 `/setup`으로 튀지 않는지 확인한다.

## 작업자 B — 여행 생성

1. **`/setup` UI (목업 데이터)**
   - 여행지(국가 검색), 기간(달력, `당일치기예요`), 예산(통화 + 금액)을 한 화면에 둔다.
   - 04(미완성)와 05(입력 완료) 상태를 둔다. 05에서는 `N박N일`·예산 요약을 보여주고 `다음`을 활성화한다.
   - 스토리를 함께 작성한다.
2. **폼 검증**
   - 필수값, 도착일 ≥ 출발일, 당일치기는 두 날짜가 같음.
   - 날짜는 `YYYY-MM-DD`로 다룬다(`toISODate` 방식 유지).
   - 금액은 양수만 받는다.
3. **06 확인 바텀시트 → PR #1 (UI만)**
   - 여행지·기간·예산 요약과 `수정` / `확인` 버튼을 둔다. `수정`은 시트만 닫는다.
4. **저장 연결 (A의 PR #1 머지 후)**
   - `확인` → `createTrip` 한 번으로 예산까지 함께 저장한다.
   - 제출 중에는 버튼을 비활성화한다.
   - 실패하면 시트와 입력값을 유지하고 에러를 표시한다.
   - 성공하면 `router.replace('/home')`로 이동한다.
5. **진입 경로 연결 → PR #2**
   - 온보딩 두 버튼과 `+ 새 여행`(C 담당 버튼)에서 `/setup`으로 오게 한다.
6. **여행 정보 수정 모드** (§7 진입점 확정 후)
   - 같은 폼을 수정 모드로 열고 `updateTrip`으로 저장한다. insert하지 않는다.
7. **1.x 라우트 정리 → PR #3** (§7 결정 후, 마지막)
   - `setup/{country,region,date,confirm}`, `/budget`, `/nickname`을 삭제하거나 리다이렉트한다.
8. **확인**
   - 중복 클릭 시 여행이 하나만 생기는지 확인한다.
   - 네트워크 실패 시 입력값이 남는지 확인한다.
   - 성공 후 뒤로가기로 폼에 돌아오지 않는지 확인한다.

## 작업자 C — 홈 이후 화면

1. **BottomNav → PR #1 (작게, 빨리)**
   - 순서를 홈 · 지난 여행 · 마이페이지로 바꾼다.
   - `/travels/*`에서 `지난 여행`을 활성으로 표시한다.
   - 07·09·10·11·12에만 노출한다.
   - 스토리를 갱신하고, ui 정리 담당자와 먼저 맞춘다.
2. **`/travels` 지난 여행 목록 (목업 데이터)**
   - 카드: 국기, 여행명, D+N, 기간, 예산 사용률 진행바(초과 시 빨강).
   - `+ 새 여행` 버튼을 만든다. 디자인은 §7 결정을 따른다.
3. **`/travels/[id]` 여행 상세 (신규)**
   - 총 지출 / 남은 금액 / 소비율을 보여준다.
   - 지출은 N일 차별로 그룹을 나누고 날짜별 합계를 표시한다.
4. **`/expense` 수정·삭제 모드**
   - 지출 항목에서 들어오면 값을 채워 연다. 수정은 update, 삭제도 가능하다.
   - 저장하면 들어온 화면(홈 또는 상세)으로 `replace`한다.
   - 제출 중에는 버튼을 비활성화하고, 실패하면 입력값을 유지한다.
5. **데이터 연결 (A의 PR #1 머지 후) → PR #2**
   - 2~4를 실제 훅에 연결한다.
   - 지출이 바뀌면 홈·상세·목록 요약 수치가 갱신되는지 확인한다.
6. **마이페이지 게스트 상태 → PR #3**
   - 게스트에게는 로그아웃 대신 `구글 로그인` 버튼과 "이 기기에만 저장" 캡션을 보여준다.
   - 실제 로그인·이전 로직은 A 7단계와 연결한다.
7. **확인**
   - 지출 없음, 예산 초과 상태를 확인한다.
   - 여러 여행이 있을 때 다른 여행으로 잘못 돌아가지 않는지 확인한다.
